## How each engine declares a reference

| | Field type in code | In memory | On disk |
|---|---|---|---|
| **Unity, hard** | A `UnityEngine.Object` field (`Texture2D tex;`) | A managed pointer to the loaded object (M) | `{fileID, guid, type}`: the asset file's GUID from its `.meta`, plus the object's id inside that file (M) |
| **Unity, lazy** | `LazyLoadReference<T>` | One `EntityId`; "loaded only when accessed and not at deserialization" (U) | Same `{fileID, guid}` pair (M) |
| **Unity, Addressables** | `AssetReference` / `AssetReferenceT<T>` | `m_AssetGUID` string plus an optional sub-object name; the loaded object is cached on the field (U-addr) | The GUID string (U-addr) |
| **Unreal, hard** | `UPROPERTY() TObjectPtr<UTexture> Tex;` | A pointer to a loaded `UObject` (E) | An index into the package's import table, which names the other package by path (M) |
| **Unreal, soft** | `TSoftObjectPtr<T>` / `FSoftObjectPath` | "Stored as a string", plus a cached weak pointer once resolved (E; the weak pointer is M) | The object path string (E) |
| **Godot** | An exported `Ref<Resource>` property, e.g. `@export var mesh: Mesh` | `Ref<>`, an intrusive reference count: `Resource` derives from `RefCounted` (G) | `ExtResource("1_7bt6s")`, a file-local id into the file's `[ext_resource type=… uid=… path=… id=…]` header table (G-doc) |

**Two patterns, not three.** Unity's hard field and Unreal's `TObjectPtr` are the same shape: a
live pointer in memory, a stable identity on disk, and the loader resolves one into the other.
Unity's lazy and Addressables fields and Unreal's soft pointers are the other shape: the
identity *is* the in-memory value, and resolving it is a separate, later step. Godot has only
the first shape for assets, and gets lazy loading from `ResourceLoader.load_threaded_request`
in script instead of from a field type (M).

**Godot's file-local table is the one structural outlier.** A payload never holds the global id.
It holds a short local key, and the header maps that key to `uid` and `path`. So the list of a
file's dependencies can be read from the header alone, without decoding a single property
(`ResourceLoaderBinary::get_dependencies`, G).

## Entity references inside a scene

| Engine | Shape |
|---|---|
| **Unity** | A field of a component type (`Transform target;`) is a plain object reference. In the scene file it is `{fileID: N}` with no `guid`, where N is the target's id inside the same file (M). |
| **Unreal** | An `AActor*` property on an actor in the same level is a hard pointer, saved as an export index in the level package (M). A reference across levels must be soft: `TSoftObjectPtr<AActor>` (M). |
| **Godot** | A `NodePath`, relative to the owning node (`NodePath("..")`). An exported property typed as a `Node` is still saved as a `NodePath`, and the node's header lists it under `node_paths` so the loader resolves it after the tree exists (G-doc). Since 4.6 a node also carries a `unique_id` (G-doc). |

All three resolve entity references **after** every object in the file exists. None remaps them
inside the per-object read. That is the same two-pass order [[Scene - Design]] § *Registration
and serialization seam* already asks for ("translate references to authoring IDs and remap on
load").

## One walk: save, load, cook and release

| | Save and load | Cook or bake | Release |
|---|---|---|---|
| **Unity** | The native serializer walks serializable fields (M) | The build collects dependencies of the scenes in the build list; the editor exposes the same walk as `AssetDatabase.GetDependencies(path, recursive)` and `EditorUtility.CollectDependencies(roots)` (U). Addressables targets must be marked addressable, or they are not in the catalog (U-addr). | **No per-field release.** Unused assets are found by a reachability scan, `Resources.UnloadUnusedAssets()` (U), which also runs on a non-additive scene load (M). Addressables is the exception: `AssetReference.ReleaseAsset()` releases a counted load operation (U-addr). |
| **Unreal** | `Serialize(FArchive&)`; every `UPROPERTY` is serialized by reflection (M) | The editor reads every `UPROPERTY` reference at startup into the AssetRegistry, and the cooker queries it. **Soft references count by default**: "UObject*, TObjectPtr, TSoftObjectPtr, and FSoftObjectPath all create a runtime reference" (E, cooking reference). A field wrapped in `#if WITH_EDITOR` is excluded (E). | **Garbage collection.** A `UPROPERTY` `TObjectPtr` "is a strong reference … that impacts garbage collection" (E); the collector walks reflected properties to find reachable objects (M). Nothing calls release. |
| **Godot** | The saver walks the property list, filtered by `PROPERTY_USAGE_STORAGE`, and assigns an `ext_resource` id to each external `Resource` it meets (`_find_resources`, G) | Export with *selected scenes* walks the file system's dependency index, which comes from those headers (`_export_find_dependencies`, G). The default export ships **every** resource, with no walk (G). | **Reference counting.** The last `Ref<>` dropping deletes the resource, and `~Resource` removes it from `ResourceCache` (G). |

**One walk serves everything in Unreal only**, because reflection already enumerates every
property. Unity and Godot each have one walk for save and load, and get the dependency list a
second way: Unity from the editor's database, Godot from a header the save walk wrote. Release is
never a walk in Godot (counted), and is a whole-heap reachability scan in Unity and Unreal.

## Mapped onto `visit`

What TechEngine has today: `visit(Archive&, T&)` is a template over the archive
(`engine/core/include/TechEngine/core/scene/components/Transform.hpp:44-45`), `Writer::field`
calls a `write` overload or falls back to `visit`
(`engine/core/include/TechEngine/core/serialization/Writer.hpp:72-80`), and the registry stores
`writePayload` and `readPayload` adapters per component
(`engine/core/include/TechEngine/core/scene/ComponentRegistry.hpp:24-25`). `ResourceId` has
neither a `write` overload nor a `visit` yet. ADR-024 §3 fixes that a handle owns nothing and
the count is per entry; §7 fixes that a replicated component carries the id, never the handle.

| Engine pattern | How it would sit on `visit` | What it costs or conflicts with |
|---|---|---|
| **Unity / Unreal hard**: a reference type holding the handle, written as its id | A small type with `visit` that writes and reads the id. The handle is filled by a remap pass after the read, the same way entity rows are. | The component must hold the id as well as the handle, or ADR-024 §7's replication rule has nothing to send. Both fit in 16 bytes. |
| **Unreal's single walk**: a third archive that only collects ids | A `Collector` archive whose `field(ResourceId&)` appends to a list and ignores everything else. ADR-016 §2 already names a third visitor (the inspector). | The bake and the release then use the same description as save. The archive must ignore every other field cheaply. Templates make that free at run time. |
| **Godot's header table**: dependencies without decoding | The scene writer collects ids during the write and emits them as a table in the scene header ([[Resources - Design]] § *Scene assets*). The bake reads the table. | It is a format bump (version 2), and it duplicates information the payloads already hold. It is what makes a dependency query cheap without loading component code. |
| **Unity / Unreal soft**: the id is the value | A field that is just a `ResourceId`, resolved on use. | This is ADR-024 §5's soft reference, built with A1. Unreal cooks soft references by default; the bake would have to follow them too, or they break in an exported build. |
| **Godot release**: an owning counted reference | A field whose destructor releases. | **Contradicts ADR-024 §3** (the handle owns nothing, is trivially copyable). Listed for completeness only. |
| **Unity / Unreal release**: reachability scan | Nothing in the field; a scan finds unused entries. | Contradicts ADR-024 §9 (eviction is explicit release only). Listed for completeness only. |

## Questions S8-D1 has to answer

These are the forks the comparison exposes. The brief does not answer them.

1. **What does the field hold in memory:** the id only, the handle only, or both? ADR-024 §7
   rules out "handle only" for any component that will replicate.
2. **Who finds the references for the bake and for release:** a third archive over the same
   `visit` (Unreal's one walk), or an id table the writer emits (Godot's header)? The two can
   coexist: the archive could be what fills the table.
3. **What releases a reference when a component is removed:** the same collecting walk, run by
   the storage on remove, or a per-type hook in the registry next to `writePayload`? A
   destructor that releases is ruled out by ADR-024 §3.
4. **Does one field type serve both `Entity` and `ResourceId` references?** All three engines
   use two different mechanisms for the two, and all three resolve entity references after the
   whole file is read.
