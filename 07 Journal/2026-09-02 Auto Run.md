### The fix, and the one thing it cannot prove

`Log.hpp` fell back to `TRACE` whenever the define was absent, so a TU including the header
without linking `base` compiles every Trace and Debug call site into a Release build. It now
follows `NDEBUG`, which is the only config signal such a TU has. `RelWithDebInfo` therefore
lands on Info where the link would have given it Debug — the quieter side, which is D1's own
reasoning and not a new decision.

**The test is deliberately not a test of that branch.** D1 asked for a case "mirroring
`AssertTests.cpp`'s config-table case (it compares the library's compiled view against the test
TU's)", and that is what shipped: the library filters on the value it was compiled with
(`Log.cpp:347`) and the macros on the value the including TU sees, so dispatching past the
macros at all six levels and counting survivors pins the two together.

| | Covered by the new case? |
|---|---|
| The define reaches the library and the TU, and they agree | **Yes.** This is the shape `TE_ASSERT_DEV` already had and this gate did not. |
| The fallback's own `NDEBUG` branch | **No.** Nothing in the tree reaches it. |

Covering the second row needs a TU that `#undef`s the gate before including the header, in its
own file because the undef would poison every other case in `LogTests.cpp`. That is a second
source file and a `CMakeLists` entry for a branch no production TU reaches, so I stopped and
left it to you rather than widening an unattended diff.

**I did check the case is not a tautology.** Reconfigured with `-DTE_LOG_ACTIVE_LEVEL=3`, the
case still passes and its expected count moves with the define, so it tracks the gate rather
than a hardcoded number.
